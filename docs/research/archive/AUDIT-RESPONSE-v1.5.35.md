### 2-1 全息屏障：这条修复没生效，而且它想修的东西不是 bug

**(a) "无目标=自己"在引擎里不成立。** 我直接喂引擎三种目标：

```
HOLO target=0(自己)   ⇒ outcome=ok  花1ジ  holoSet 事件 = {pid:0, target:1}   ← 被改送给 1 号
HOLO target=2(对手)   ⇒ outcome=ok  花1ジ  holoSet 事件 = {pid:0, target:2}   2号身上架势=proto  ✓
HOLO target=null      ⇒ outcome=ok  花1ジ  holoSet 事件 = {pid:0, target:1}   ← 同样被改送给 1 号
```

引擎 `resolve.js:183` 的 `holoShieldFrom` 明写 `if (i === pid) continue; // 自己给自己套不算`，
而 `targetOf()` 把 null/自己一律回退成"第一个存活对手"。⇒ **候选集里那个"自己"是一个幻影选项**：
策略以为自己在做 A，引擎执行的是"把盾给 1 号"。**实测它被选中 35/330 次（11%）**——
每一次都是策略与引擎语义不一致的样本，而且它会把错误的归因喂回训练。

**(b) 用户裁定：全息屏障本来就不能给自己，自保用的是原型制御。** 所以"AI 把盾送给对手"**不是 bug，是这张卡的定义**；
真正的问题是**它用得太频繁**（自对局 5.5 次/局），而按用户的说法这张卡应当等到 AI 学会结盟才常见——
而"结盟/威胁建模"早已被裁定为不做。
⇒ 修法应当是**把那个幻影候选删掉**（`candidatesFor` 对 `target:'other'` 不该给 null/自己），
然后正面处理"过度使用"：要么给一个规则形状的先验（例如"只有当目标不是当前血量最高者时送盾才计分"），
要么承认结盟不在范围内、把 C 门槛按新语义重新标定并**写清理由**——而不是 `--force` 过去。
（我测的送盾分布：35% 给血量最高者、72% 给最弱者、其余给中间；"给最弱者"其实接近结盟逻辑，所以这条并非纯噪声。）

### 2-2 平局口径：修得对，但用它推翻上轮结论是过度延伸

`checkOver` 我用 `git log -L` 查过：**自 v1.4.0 起一字未改**，一直是"到上限按血量、同血量判平"。
他改的是**体检自己的 `drawRate`**（原来把"全活"一律记成和）。而我上轮的农夫场数字取的是**引擎自己的 `state.winner`**，
所以从来没被这个错误影响。为了把这件事钉死，我这次直接统计"我方血量明明最高、却被记成平"的局数：

```
[multi 农夫场] 线上 胜0% 平100% │ 我血 3.00 vs 对手最高血 3.00 │ 血量最高却记平 0/60
[long  农夫场] 线上 胜0% 平100% │ 我血 0.00 vs 对手最高血 0.00 │ 血量最高却记平 0/60
（v7press-36、eco-34 同样：0/60）
```

⇒ **"农夫场 0% 胜 / 100% 平"不是口径假象，是真的打不死人**：三冠军在 4 个只按 ジ 的对手面前
最终血量全部 3.00 对 3.00（long 里全被终局收缩耗死成 0 对 0）。这条结论**原封不动地继续成立**。

## 5. "打断环"四次失败：还有三个障碍他没找到

### 5-1 **[实测] 奖励在结构上无法归因——`voided` 事件不记施法者**

`resolve.js:19 setVoid(state, pid, by)` ⇒ 事件形状 `{type:'voided', pid, by}`，
其中 `by` 是**原因字符串**（`'miniT'`/`'避雷针'`/`'真正的落雷'`…），**不是施法者的 pid**。
所以 `countRingBreaks` 只能写成 `if (miniT > 0) breaks += pending.length;`。我直接调这个纯函数做反例：

```
A 我小雷砸在开环者身上、作废成功            ⇒ 1.5   （正确）
B 我出过小雷但砸的是别人，是 pid3 作废的    ⇒ 1.5   ← 与 A 同分！
C 我全程没出小雷（pid2 出的、他作废）        ⇒ 0     （正确）
D 环第一次启动（真实 delta=1）+ 我出小雷      ⇒ 0     ← 首次开环不被识别
E 对手只是被避雷针回馈 +4 ジ（非环）+ 我出小雷 ⇒ 0.5   （判据把非环的大额 ep 当开环）
```

而代码里那行注释写的是"**作废加分必须由我出小雷引起**"——**注释比代码强**。`D39` 的断言用的是
"我出小雷 + 开环者被作废"的合成流，恰好**测不到 B 这一格**。
⇒ **最小修法**：`setVoid(state, t, SK.MINI_T, c)` ⇒ 事件加 `byPid`；`countRingBreaks` 要求 `pending` 里 `byPid === seat`。
两行代码，之后"打断"才是可学的信号。**在这之前，任何奖励侧/课程侧的尝试都会撞同一堵墙。**

### 5-2 **[实测] 反环教师的触发条件比"开环"宽 300 倍**

教师（`evo.js:1139`）的条件是 `对手 ep >= 2`。我在真实自对局里逐决策统计：

```
"有对手 ep>=2" 成立  45%（2034/4549 个决策）
"有对手真在开环(ringStreak>=1)" 成立  0.15%（7/4549）
```

⇒ 教师实际上在教"**只要有人兜里超过 2 ジ 就砸小雷**"，而不是"砸那个滚环的"。
被示范出来的动作与"开环"这个状态**几乎不相关** ⇒ 模仿学习把动作分布拉宽了，却没有建立动作—状态关联，
这正是"课程/示范"那一枪也没能复现出小雷（仅 1 次）的原因。
⇒ 教师条件应改成 `ringStreak >= 1`（或 `lastSkill === ring`），并且**与 §5-1 的归因一起改**，否则示范出来的动作仍然拿不到可归因的奖励。

### 5-3 **[实测] "开环判据"漏掉第一次启动**

真实事件流：聚能环两次出手的 ep delta 是 **`1` 然后 `2`**（首次 +1、第二次 +2）。
而 `countRingBreaks` 的判据是 `delta >= 2` ⇒ **环的第一回合不被识别为开环**，
于是"越早打断越该得分"这件事在奖励里是反的（晚了才有信号）。

### 5-4 关于"要不要加维度"：他的结论我同意，但**论证要换**

他的说法是"信息本来就在：每个对手一个槽位（含其 ep）⇒ 从 ep 轨迹可推出"。两处不成立：
- **每对手槽位的 10 维里没有 `ringStreak`**（`policy.js:222-226` 实测：存活/血量/ep/持珠/刚蓄能/lastSkill×3/ep≥2/ep≥5）；
  `ringStreak` 只在 base 段以 **`anyOp(o => o.ringStreak)/3`（聚合"有人在滚"）** 出现 ⇒ **知道有，不知道是谁**。
- **"从 ep 轨迹推出"对这个架构不可能**：`value()` 是**单快照打分**，跨回合记忆只有 3 步 `lastSkill` 历史，**没有 ep 历史**。

但结论仍然站得住，只是理由要换成这个：**每槽的 `lastSkill` 能认出滚环者**（滚环者上一手就是 `ring`）⇒
**表达力够用，缺的是探索与归因**。所以：
- 若走"定向探索"：**必须同时做 §5-1 的 `byPid`**，否则逼出来的动作拿不到可归因的奖励，第五次还会失败；
- 若哪天真要加维度，**只需在每对手槽位加 1 维 `o.ringStreak/3`**（+5 维、`FEAT_S 213→218`），
  而不是新造概念——这一点他自己已经说对了。

### 5-5 **[实测] 他提的验收标准会被自己的手段满足**

`ringWallProbe.miniTCasts` 数的是**引擎事件流里"我这一手的 action"**（`audit-lib.mjs:179`）。
一旦按他的方案在 chooser 里加 ε-强迫，**被强迫出来的出手同样会进这条计数** ⇒
`miniTCasts ≥ 5/20 局` 变成**由干预本身保证、不可能失败**的断言——正是他们 `L1` 教训里"恒真式"的那一类。
⇒ 验收必须改成两栏：**关掉强迫后的自然小雷数 > 0**，以及 **`voided` 且 `byPid===我` 的次数 > 0**（这条依赖 §5-1）。
