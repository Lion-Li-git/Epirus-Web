> 数据全部从 GitHub API 现读（`list_workflow_runs` / `list_workflow_jobs`），时刻不是估的。

## 二、决定性证据：同一份代码，相邻两趟差 2 倍

| run | sha | 这一笔改了什么 | train-runner |
|---|---|---|---|

| 273 | `a989d8f`（v1.7.107） | **纯文档/数据**（32 枚复测） | **1616s** |

273 与 274 的**代码完全相同**，一个 1616s、一个 841s ⇒ **摆动在机器侧**（免费档 runner 异构：2 核/4 核、不同 CPU 代），我们控制不了。
其余 15 个部分在同一时段内一秒没变（`train-evo` 稳定在 649–655s）⇒ 只有 `train-runner` 吃这个亏，因为它是唯一**大量 spawn 子进程**的部分。

## 三、已经做的一条（v1.7.116）：并发上限按核数

`tools/np-parallel.mjs` 原来把并发上限**写死 7**（照 18 核开发机调的）。CI 2 核 ⇒ **7 倍超订**。

```js
const CPUS = os.availableParallelism ? os.availableParallelism() : os.cpus().length;
const autoMax = Math.max(2, Math.min(7, CPUS));   // 18 核 ⇒ 7（旧行为）；2 核 ⇒ 2
const cap = +process.env.EPIRUS_BATCH_MAX > 0 ? +process.env.EPIRUS_BATCH_MAX : autoMax;
```

**实测效果**：run 286（改前）train-runner **1669s** → run 287（改后）**1435s**，**−14%**。
⇒ 有效，但只能买到这么多：**超订修掉之后，剩下的上限是单核速度**，那是 runner 决定的。
（本地 `--part=train-runner` 改后仍 **31/31 绿**、~300s，行为逐字不变。）

## 四、唯一还能真正控制的是"少干点活"：拆 `train-runner`

现在 `train-runner` **一个 job = 整趟的 98%**（1435 / 1461）。

| | 现在 | 拆成两半后（预估，两种机器速度都算） |
|---|---|---|
| 每半（快模式） | 820s | ~410s |
| 每半（慢模式） | 1435s | ~720s |
| **整趟墙钟** | **24 min** | **~12–13 min**（critical path 变 `train-evo` 的 655s） |

**这个杠杆和机器快慢无关**（把一份活分两份，不是让机器变快），所以它比继续调 cap 有价值。

## 五、如果开工，要注意的骨头（我从今天的踩坑里挑的）

1. **三处注册必须同时改**：部分文件的 `ords`（尾部加新号）、`#np-part-header` 的 `ranges`/`gates`、`tools/np-test.mjs` 的 `PARTS` 与 `GRP`。少一处 = **runner 直接 refuse 起跑**（`ords` 与 `t()` 调用数不配对会抛错，我今天的 D236 就是先撞的这个）。
2. **并集守卫是保险**：`node tools/gate-parts-check.mjs` 会现读校验"并集 = 279、每部分非空、归属表一致"。拆完**先跑它**再跑部分。
3. **别只对半切**：`train-runner` 里 31 条门里有几条是**唯一在跑 `spawnBatch`** 的（D176 那一族，单跑 ~59s），它们才是耗时主体 —— 按耗时聚类比按行号对半安全。
4. **CLI 的 `plan` 作业会自动读出第 17 个部分**（`--list-parts --json`），CI 矩阵不用改；**但 `gate-parts-check` 里若还有写死的 16，会静默少跑**（正是它存在的理由）。
5. **验收读 CI run 号**，不读本地秒数（本地 18 核 vs CI 2 核，快 3~5 倍，本地数字会给你假信心）。

## 六、结论一句话

**「CI 变慢」不是代码回归，是 runner 异构 ⇒ 我们只能减少工作量。** v1.7.116 已经把超订那部分修掉（−14%）；剩下的唯一杠杆是把 `train-runner` 拆成两半（~24 → ~12–13 分钟）。

## 八、⚑ 更正（10-19 22:0x，千问 §E655 的复核 + 我自己的复验）

### ① 「−14% ⇒ 有效」**不成立**，改成「未证实」

`v1.7.116` 的缺省 cap **够不到热点**：`np-parallel.mjs` 取上限是 `o.max` 优先、缺省才用 `cap`，
而耗时的调用点全都显式传了 `max`（`train-runner.mjs:1319` `max: specs.length` = 6 支臂 ‖ `:1558` `max: 2` ‖ `train-evo:2742/2761/2765` = 4/3/1）。
⇒ 全仓唯一吃到新缺省的只有 `train-evo:2748` 那三个微秒级 job。**run 287 的 1669→1428s 不能记在这把闸上。**

### ② 我 §二 那句「其余 15 个部分一秒没变」也错了

`train-evo` 在 run 286 = **352s**、run 287 = **645s** ⇒ 它自己就在 1.8× 摆。双峰 820↔1620 本来就是 ±2×，
任何 ~14% 的单趟差都落在带内 ⇒ **n=1 不许归因**（这是我今晚第三次犯同一个错）。

### ③ 「本地快」的真因不是机器，是**缓存**

`np-cache.mjs:44` `cacheOn()` **默认开**（只有 `NP_NOCACHE=1` 才真跑）⇒ 本地秒数被缓存洗过。
「验收读 CI run 号」这条仍然对，**但理由要换成"本地有缓存"**，不是"机器不同"。

### ④ v1.7.117 把闸接到了热点（这一条是**待验**，不是已验）

`np-parallel.mjs` 导出 `batchCap()`；`train-runner.mjs:1319` 改成 `max: Math.min(specs.length, batchCap())`。
本地 18 核仍是 6（= 旧行为逐字相同），CI 2 核降到 2。
**预期不买时间**（2 核上 CPU 总工作没变，只减调度/内存压力）⇒ 验收必须 **n≥3 趟 CI run**，只看这一个 job 的秒数分布。
