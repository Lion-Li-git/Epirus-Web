# 落地单 · 把 `train-runner` 拆开，让跑门的墙钟从 22.8 分钟降到 ~13 分钟（2026-10-19 下午 · 千问 · 用户点名"尽量让跑门禁的效率高一些"）

## 一、为什么是它（实测，不是我猜）

10-19 两趟全 16 部分并发（`jobs=4`，同一台 18 核机）：

| 趟 | 墙钟 | critical path |
|---|---|---|
| 15:31–15:45（脏池那趟） | 13.4 分钟（部分计时之和） | `train-runner` **1014.6 s** ‖ `train-evo` 452.4 s ‖ `probe-instruments` 98.2 s ‖ `ship-promote` 90.3 s |
| 14:44–15:07（六部分那趟） | 22.8 分钟 | 同上，`train-runner` 1007.3 s |

⇒ 并发下墙钟 ≈ 最慢那一段 ÷ 有效并行度，而 `train-runner` 一个部分就是 **1015 s**，比第二名的两倍还多 ⇒ **拆它一个等于拆掉墙钟的顶**。CI 也一样：`.github/workflows/gates.yml` 的 matrix 是 `--list-parts` 现读的（加第 17 个部分文件**不用改 workflow**），所以 CI 的墙钟同样受它顶住。

## 二、动谁的手（两处，都不改判据）

1. `tools/gates/train-runner.mjs`（31 条腿）里把**真跑训练臂**的那 7~8 条挪进新文件 `tools/gates/train-arms.mjs`；留在原部分的是纯函数/静态扫描/单元级那些（绝大多数）。按 §E654 实测的贵度排（代参 × 臂数）：
   `D135`（60 代归因）‖ `D176`（60 代 veto + 2 代对照）‖ `D185`（40 代重验池）‖ `D136`（30 代示范归因）‖ `D127`（3 代孪生臂 ×2，**今天刚补过落点的那条**）‖ `D128`（3 代）‖ `D130`（2 代 ×3）‖ `D180`（3 代）。
   ⚠ 这几条之间有共享夹具（`armBatch` / `spawnNC` 的缓存键），挪的时候**整块搬**（连它上面的 `dir` / `SEEDPACK` 定义一起），别拆一半。
2. `tools/gates/**` 的**部分文件约定**——这是这件事真正的门槛，动之前先读三处：
   - `tools/gate-src.mjs`：`partFiles()` 靠每个文件里的 `export const ords = [首条原始行号…]` **排序**并拼门体面 ⇒ 新文件必须有自己的 `ords`，且首值不能与既有部分撞序；
   - 每个部分文件顶部的 `/*#np-part-header {file,part,group,ranges,gates,patched} */`：`ranges` 是**当年从 `np-test.mjs` 切片时的原始行段**（历史来历，不参与执行）。⇒ 第一个问题就是"新部分的 header 由谁生成"：`tools/**` 里没有写这个头的脚本（只有被写出来的文件里有），说明是一次性脚本产的 ⇒ **要么找到那台脚本（在 `docs/research/archive/**` 里搜 `np-part-header` 的写入方），要么按 `ship-pool.mjs`（1 条腿的最小部分）照抄形状并让 `gate-parts-check` 认。** 这一步没弄懂之前不要动文件——半迁移的门比慢的门糟得多（我 10-19 下午就是因此没做它）。
   - `tools/gate-parts-check.mjs`：它是并集守卫（① 每条腿有归属 ② 不重不漏 ③ 每部分非空 ⇒ "空部分 = 拆坏了"）。**它是这件事的验收尺**：拆完先跑它。

## 三、验收（顺序执行，别跳）

1. `node tools/gate-parts-check.mjs` ⇒ 并集全、无空部分；
2. `node tools/np-test.mjs --part=train-runner` ‖ `--part=train-arms` **各自单跑全绿**（不并发——并发跑绿不能证明各自跑绿）；
3. **变异对照**（她的老规矩："任何'跑 X 绿'都要问坏了 X 会不会红"）：临时把挪过去的一条腿的断言改坏 ⇒ 必须只有 `train-arms` 红、`train-runner` 不许跟着红；改回来；
4. `node tools/gate-par.mjs --jobs=4`（全 17 部分）两遍 ⇒ 报墙钟；第二遍只为看抖动。**预期：critical path 从 1015 s 掉到 ~600 s ⇒ 整趟 22.8 → ~13–15 分钟**；
5. 收尾 `--group=meta` + `--only="D234 "`（我 10-19 已确认 `train-runner`/`train-evo` 都吃 `coords.tsv`/`index.html`，拆文件不改这层，但门号与并集要复跑）；
6. 顺手量一次 `node tools/gate-par.mjs --timing --part=train-runner` ⇒ 把"每条腿多少秒"落到文件里（现在只能从部分总时长反推，下次再排就没依据）。

## 四、拆之前先说清的三件事（免得变成第二次"跟着红点清"）

1. **并行度不是瓶颈**（`jobs=4` 已按内部 worker 池留余量，见 `gate-par.mjs` 头注），所以**不要靠调 `--jobs` 提速**，那只改形状不改 critical path。
2. **`train-runner` 内部已有 `spawnBatch` 并发** ⇒ 拆之后总 CPU 不变，墙钟下降只来自"两个部分可以并行、一个部分不能自己和自己并行"。若拆完 critical path 没降，说明瓶颈在单条腿（那就是 `D135`/`D176` 那两条 60 代臂自己），下一步才轮到"把一条腿拆成两个 batch"。
3. **缓存的副作用要想清楚**：`np-cache` 是内容寻址（`inputHash`）⇒ 换部分文件会改 `inputHash` 的输入吗？如果改，拆完的第一轮所有臂都算未命中、会明显变慢，**第二遍的数才是可引用的那个**（`--onlyExtra` 那类"第一遍慢"的坑本仓踩过）。

| 部分 | CI 秒 | 本地秒 | 差 |

| `train-runner` | **1175** | 1002.8 | +17% |
| `train-evo` | **639** | 446.9 | **+43%** |
| `train-env` | 184 | 123.9 | +48% |
| `ship-promote` | 126 | 84.5 | +49% |
| `probe-instruments` | 106 | 91.6 | +16% |
| `ship-feas` | 44 | 26.7 | +65% |
| 其余 10 个部分 | 25/18/5/5/3/2/2/1/1/0 | 同量级 | — |

整趟墙钟 **1210s（08:33:31→08:53:41）**，`train-runner` 一段占 **97%**。

⚑ **CI 比本地慢，而且不是均匀地慢**（短腿几乎一样，长腿 +17~49%）⇒ **任何基于本地权重的调优都要用 CI 秒数复算**。

### 二、认证口径（**v1.7.115 起生效**）

**出厂认证 = 读 CI run 号**；本地只跑改动面（`gate-par --changed` + 改动腿的 `--only`）。

理由（CI 这一档比本地那趟**强**在哪）：

| 面 | CI 绿能不能当认证 |
|---|---|
| 278→279 条门（16 部分，各一台干净机） | ✅ **强于本地**：干净克隆**不可能**有未跟踪残留造成的假红 |
| 并集守卫 `gate-parts-check` | ✅ 同一作业里现读现跑 |
| `spec-run`（2 人引擎 52 用例） | ✅ |
| **三个 CDP 浏览器步骤** | ❌ **不能**：那一档 `continue-on-error: true`（`gates.yml:146`）⇒ **红了 run 仍是 success** |

**代价（必须说清）**：红的东西会先落在 `main` 上，发现时机从 push 前挪到 push 后。
缓解：小步推 + 本地先跑 `--changed`；CI 红了就**当工时事故处理**（不是"等它自己绿"）。

**要 Browser 面进认证，得先摘 `continue-on-error` + 把 `browser` 加进 `gates` 的 `needs`** —— 那是另一个决定，未做。

### 三、拆分单的前提在 CI 上同样成立

`train-runner` 一分为二 ⇒ critical path 变成 `train-evo` 的 **639s** ⇒ CI 从 ~20 分钟降到 **~11 分钟（省 45%）**。
⚠ 拆完的验收**读 CI run 号**，不读本地秒数（本地权重表在 CI 上偏乐观）。
