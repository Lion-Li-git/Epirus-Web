### C. 训练方法论

| 认识 | 证据 |
|---|---|

## 2. ❌ 尚存的问题

### P0 — **深经济锁死（核心，未解）**

**现象**：3 人冠军 **max ep ≤ 2**；环(3ジ)、大雷(5ジ)、转移(2ジ)、电磁炮(2ジ+珠) 全无人用。

**五种尝试全部失败**：

| # | 做法 | 结果 |
|---|---|---|
| 1 | 课程式补贴（前 30% 代 regen=2…） | max ep 2 |
| 2 | 永久回放切片（~8% 局补贴，永不退火） | max ep 2 |
| 3 | 探针进选择（`min(pairSc, probeSc)`） | 冠军退化为纯防御 spammer |
| 4 | 探针修正（只奖励落地 + 门槛） | 所有候选 probeSc=0（**构造上不可满足**） |
| 5 | 脚本教师模仿（前 35% 代，退火） | max ep 2，冠军更差（藤甲 43.6%） |

**你给出的关键判断（我认同并已部分验证）**：
> **不是探索问题，是货架问题**——富经济下"只出坦克"就有 96~100%，
> 而 5 ジ 的大雷打龟缩型只有 33.3%（= 随机基线）⇒ **多攒 3 回合换不到任何 2 ジ 换不到的东西**。

**⚠️ 但我认为这条现在要打个补丁**：你测"只出坦克 96~100%"是在**3 人局**。
而用户的裁定是**大雷的优势在多人局的传导+失效+禁用**——
**它的价值可能恰恰在 3 人局里测不出来**（N22 传导集合在 3 人局只有 1 个第三方，4 人局有 2 个）。

### P0b — v1.3.54：「货架问题」拿到了**有效证据**（配对测量，含正对照）

上面第 5 条（"不是探索问题，是货架问题"）此前只有**间接**观察支撑，而那条观察的考卷本身可疑
（3 人局里"只出坦克 96~100%"）。v1.3.54 用 `tools/subsidy-diag.mjs` 对线下冠军做**同一批种子**的
配对测量，直接问"**钱到底买不买到东西**"：

| 档位 | 夺 1 率 | 深技能（cost>=3）/局 |
|---|---|---|
| 原生 ep=0 | 26.7% | 0.00 |
| 开局白给 ep=6 | **46.7%（+20pt）** | **0.00** |
| 承诺 h=2 + 白给 4 | 36.7%（+10pt） | 0.00 |
| regen=2（永久通道） | 43.3%（+16.7pt） | 0.00 |
| **正对照：脚本鲸鱼（总挑最贵）** | — | **3.00**（20 局打出 `bigT` 60 次） |

**正对照是关键**（反证法）：它证明"深技能"这个口径**可被触达**，所以冠军的 `0.00`
是**策略的选择**，不是测量死角。⇒ **钱能买到胜率，但买不到贵技能**：
冠军变强靠的是更频繁地出**便宜**技能。**货架问题成立。**

**⇒ (c) 的判决**：把"补贴局夺 1 率"当选择门槛**在 3 人局不成立** ——
它反映的是**补贴强度**，不是候选的深经济能力，只会给选择注入噪声。
故 `SUBSIDY_MIN` **默认 0（关闭）**，行为与改动前一致；留给有货架的 **5 人局**
（千问实测 `大雷 − 坦克 = +26.7pt @5P`）重新标定。机制本身（h 基因 + 分巢精英）已落地并
**接线有实测证据**（30/30 代 `commitBest>0`、`hDist` 逐代漂移），因为它是对的东西、只是考卷不对。

**顺带挖出一个真问题（差点被我写成一条错误的更正）**：`js/core/play.js:50-53` 在**调用 chooser
之前**就算好 `legal[i].affordable`，返回后又用**那个旧值**把买不起的选择强制改回ジ。
我据此一度判定 `evalEconProbe`（第 4 条尝试）的"构造上不可满足"是**测量假象**，
**差点写进代码和文档**。实测（`tools/grant-mech-diag.mjs`）**否定了它**：
`affordable` 序列 = `[false,false,false,true,true,true]` ⇒
**只对每局第 1 回合无效**（改的是真实 state，会留到下一回合）。
所以那条历史结论**只有首回合是盲的，其余仍然有效**。
已修掉那一个回合的盲区，并钉成用例 **L4**（`np-test`）。

#### P3.3 的更正（v1.3.56）

原文写"`trainer.js` 的 `budgetMs` 分帧预算 ⇒ 浏览器里点『开始训练』本质上不可复现"。
**两处都站不住，撤回**：

1. **那段代码根本没被使用**：`#btn-train` → `ui.js:777` `new EventSource(base + '/train?…')`
   → **Node 服务**；`trainer.js:57 startTraining` 是**死代码**（全仓零调用方）。
   而 `js/train/trainer.js` 与 `js/ui/ui.js` **自 v1.3.23 起就没被改过**。
2. **`budgetMs` 不改变算出来的东西**：`while (… Date.now() - t0 < budgetMs)` 只决定**何时让出帧**。

**真因是"输入没被记录"，不是"随机源"、也不是分帧**：
`index.html:75` 的 `#tr-fresh` **默认不勾** → `ui.js:718` 不发 `fresh=1` →
server `fresh=false` → `seedP = loadSeedN()` **读 `js/bundled-champion-3p.js`** 热启动
（1/3 种群由它变异而来）。那个文件每训练一次就变 ⇒ 下一次运行**输入不同**。
与 v1.3.50 给 CLI 定位的根因同类（"热启动读自己的产物"）。

**实测**（同输入冠军、同 `?seed=5`、不传 `fresh=1`、两次之间还原输入冠军）：
20 代 SSE 记录 (2) 逐字节完全一致，整个流唯一差异是 `done` 的 `secs`（墙上时钟）。
⇒ **给定 (seed, 输入冠军)，浏览器默认配置是可复现的**。

**修法**：server 的两条路径都把可复现输入记进 meta —— `seed` / `hotstartFrom`
（输入冠军的**权重数组** sha1，沿用 v1.3.36 的"只哈希权重"口径）/ `fresh` / `workers`；
钉成 np-test 的 **L3** 断言。

**仍缺**：① UI 不发 `seed`（所有浏览器运行都用 `seed0=0`，可复现但无法配对）；
② `repro-check` 仍未覆盖 server 的**非 fresh** 路径（= 浏览器默认配置，即未做的 F）。
