## 2. ✅ 训练不可复现 —— **已解决**（且我原来的证据是假阳性）

### 最终结果（千问定位 + 修复后实测）
```
两次 ?seed=42（gens=100 n=3 pop=8 gpo=6 fresh=1）：
  第 1 次  整文件sha=fe73de50cd24d1a2   仅权重sha=cd32f2407ab7244c
  第 2 次  整文件sha=5a01db5f57ec27e6   仅权重sha=cd32f2407ab7244c   ← 权重完全一致
```
⚠️ **我原来的"不可复现"证据是假阳性**：我哈希的是**整个文件**，而
`writeBundleMP` 会把 `ts: new Date().toISOString()` 写进 META ⇒ 每次必然不同，**与权重无关**。
**千问预判了这一点，并提醒改哈希 `a` 数组 —— 他是对的。**

### 真正的根因（千问定位，两处，都在 **Node 作用域**）
1. **`train-server.mjs` runTrainN 的繁殖段**（原 314-316）用裸 `Math.random()`：
   ```js
   const a = elite[Math.floor(Math.random() * elite.length)];
   const b = scored[Math.floor(Math.random() * Math.min(6, scored.length))].params;
   let child = Math.random() < 0.5 ? P.crossover(a, b) : a.slice();
   ```
   **`__seedSandbox` 只替换 vm 沙箱内的 `Math`，管不到 Node 全局** ——
   所以我在沙箱里修好的那 5 处（evo.js 4 + bots.js 1）都生效了，**唯独这三处从未被播种**。
   已改为显式播种流 `breedRng = T.mulberry32((SEED0||1)*100003 + gen)`。
2. **`runTrain`（2P 路径）的 `seedBase = (r+1)*7919 + (Date.now()%1000)`** ——
   决定"选哪个冠军"的评测种子来自**墙上时钟**。已改为 `cfg.seed0 * 100003 + (r+1)*7919`。

### 千问排除的嫌疑（记下来免得重查）
- **worker 聚合是确定性的**：`paralleltrain.mjs` 的 `evalAll` 用 `by[r.idx] = r` 回填、
  再按 `i` 顺序循环写回，`Promise.all` 的完成顺序**不参与任何决策** ⇒ "任务调度顺序依赖"排除。
- **评估层与引擎是干净的**：`scoreMemberN` 同参数两次调用逐位一致
  ⇒ 地雷 AoE 那次重写**没有引入不确定性**。

### 新增防回归断言（千问建议的"硬规矩"）
`tools/np-test.mjs` 加了 **REPRO 用例**：扫描 `server/*.mjs`，
**禁止裸 `Math.random(` / `Date.now(`**（白名单：`mulberry32` 兜底、`const t0 = Date.now()` 纯计时、
超时判断、时间戳、cache token、注释）。**下次再有人在外面写一句裸随机会直接红。**
（本轮就是靠它先抓到 3 条误报、再确认已无漏网。）

### 仍未处理（千问列的"跨机不可复现"三条，建议后续一起收）
1. **worker 数改变结果**：`num = cpus().length - 1`、`chunk = ceil(pop/num)`，所有 worker 共用
   同一个 `EPIRUS_SEED0` ⇒ 每个个体拿到的随机流偏移随 worker 数变化（8 核 ≠ 18 核）。
   建议：`seed = SEED0*1000 + workerIndex`，并把 worker 数写进冠军 meta。
2. **同种子 worker 是相关样本**：会系统性低估个体间差异、**放大假信号**。
   §3 那个"同设置内极差 7.4~7.6pt"里可能有相当一部分来自这里 ——
   **给每个 worker 不同种子后应重测噪声下限，我预期那个数会明显变小。**
3. **两处墙上时钟中断**：`train-server.mjs:311` 的 30 分钟上限（在生成循环内，建议改按代数计）；
   `trainer.js:74-76` 的 `budgetMs` 分帧预算 ⇒ **浏览器里点"开始训练"本质上不可复现**
   （每帧几代取决于机器快慢），要么在 UI 注明，要么改成固定每帧 N 代。

## 3. ⭐ 意外收获：噪声下限的标定（本文档最重要的实证）

### 实验：火弱（藤甲 debuff）持续性
- 用户提过你的建议：**把火弱从"一回合结束"改成"保留到下一次触发"来提升藤甲**。
- 做法：`resolve.js` 加训练侧开关 `EPIRUS_FIREWEAK_PERSIST`（**默认关，shipped 规则一字未改**）：
  打开时 `fireWeakNext` 不在 `startTurn` 清除（每回合重新武装），直到被火焰伤害兑现才清除。
- 按用户建议用 **3×200 代**（而非 1×600）。

### 结果一：胜率无可测效果
| | firstRate（3 次） | 均值 |
|---|---|---|
| 基线 | 0.463 / 0.389 / 0.458 | **0.4366** |
| 持续 | 0.393 / 0.469 / 0.439 | **0.4338** |
差 **−0.3pt**，而同设置内极差 **7.4~7.6pt**。

### 结果二：**藤甲在全部 6 个冠军里都是 0.0%**
⇒ **这个开关是"可证明的 no-op"**：没人出藤甲 → 没人被挂 `fireWeakNext` → 开关永远读不到有效分支。

### 结果三（关键）：正因它不可能有效果，差异就是**纯噪声**
| | 最高 ep | 贵技能出手 |
|---|---|---|
| 基线 3 种子 | 1 / 1 / 1 | 0% / 0% / 0% |
| 持续 3 种子 | 1 / **2** / **2** | 0% / **33.3%** / **23.8%** |

**一个可证明无效的干预，造出了"2/3 种子达到 maxEp=2 且 24~33% 贵技能" vs "0/3"。**
若我们不知道它是 no-op，**这看起来完全像一次成功的规则改动**。

⇒ **在 n=3 × 200 代下，噪声足以制造"2/3 vs 0/3"量级的假信号。**
**因此：在可配对设计到位之前，规则改动的前后对比一律不可信。** 这也直接说明 §2 为什么是地基。

你建议"n=3 方差这么大，要不要提到 4 个种子"——**我们做了 3 种子对照，结果推翻了我自己的一个错误决定**：

## 5. 规则侧：N20 地雷 AoE（用户裁定，已实现并全绿）

### 偏差的由来（很典型）
`mineChain` 一直是 2 人时代口径——**只让"攻击者"受 1 点火伤**。但 2 人局里
「全场其他角色」与「攻击者」**恰好是同一人** ⇒ **两种读法在 2 人下无法区分**，
multi 框架加入时没回头核对 ⇒ 该偏差**只在 N≥3 显形**。

### 正确规则（用户裁定，例子逐项核对过）
- **直接触发**（X 被非狙击枪攻击）：除 X 外**所有存活角色**各受 1 火伤，**无次数上限**。
- **间接触发**（挨了地雷伤害且自己装着雷）：所有间接触发者**合并成一波**，
  打**除这些间接触发者之外**的所有存活角色。
- **火弱逐目标**（藤甲挂在被攻击者身上，只对被挂者 +1）。
- **地雷伤害无来源**（`source=null`）⇒ 不被铁索共享 / 不被转移 / 不被大雷传导。

### 实现要点
`mineChain` → `mineHit` + `mineResolveAll`；伤害阶段**只记 `_minePending`**，
在 `resolveActions` 末尾统一结算 —— 为了做到**「直接优先」**：
d 双枪同时打 a、b 时，若边打边结，a 的雷波会把 b 的雷**提前**当间接消耗掉，
b 的直接触发永不发生（实测 b 只掉 2 血，应为 3）。

### 用例（N≥3，2 人用例天然测不出）
`N20a` 直接触发+间接合并 ✔ / `N20b` 直接触发无上限（双枪）✔ /
`N20c` 无来源不被铁索共享 ✔ / `N20d` 火弱逐目标 ✔ / `N20e` 狙击枪豁免只针对那一次 ✔

### 顺带抓出的一个**我引入的真 bug**（v1.3.19 → v1.3.31 修复）
`MINE_TRIGGER` / `REFLECTABLE` 都**按 `via` 查表**且**不含 `dualGun`**。
我在 v1.3.19 做"双枪走数据表"时把 `via` 从 `SK.GUN` 改成了 `SK.DUAL_GUN`
（**注释里明明写着"via 仍按枪口径"，实现却改了**）⇒ **双枪第一枪不触发地雷、也不被反弹**。
教训：**"技能走数据表"只该动数值字段；`via` 是语义键，不能顺手改。**

## 6. 其他已确认结论（简化，细节见 CHANGELOG）

- **藤甲被免费 `反弹` 严格支配**：反弹 0 ジ、藤甲 1 ジ、防御效果相同（藤甲额外给对手火弱）。
  强制把藤甲换成反弹，avg **97.6% → 98.3%**。**这才是藤甲没人用的原因，不是火弱时长。**
- **地雷与大雷在脚本内互斥**（地雷 3 ジ vs 大雷 5 ジ，花了 3 就到不了 5）；
  且"结合对手 ジ 数"是**双刃**的：`guardspam`/`protowall` 把 ジ 全花在架势上、`ep` 常为 0，
  用 `ep>=1` 当门槛会**恰好排除最爱摆架势的对手**。
- **`deepsaver` 的教训**：初版"买得起就放地雷"→ 最高 ep 只到 3；改读 `lastSkill===PROTO` →
  120 次检查 **0 次命中**（拿上一回合的招当这一回合的意图，逻辑错位）。
  正解是**可观测的历史频率**（近 5 回合架势次数）。
- **`heavyfire` 不是深经济探针**（最高 ep 2 / ep≥3 占比 **0.0%**），我 v1.3.23 的判断是错的。
  池里本来就有会攒的（`breakdef` 最高 ep 5 / ep≥3 **43.4%**；`farmer` maxEp 10 / 54.8% 但不还手）。
- **座位偏置**（也已修）：同优先级按 pid 升序 → 破防脚本座位 1st 率 73.5/14.5/0.0 → 32.9/31.5/35.7。
