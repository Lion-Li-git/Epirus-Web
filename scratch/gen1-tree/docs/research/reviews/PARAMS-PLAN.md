# 给冠军"加参数量"的评估（2026-09-13，v1.5.17）

> **结论先写**：① **兼容性可行** —— `js/train/policy.js` 已有一套"形状从参数量反推 + 旧维度裁掉"的机制
> （**教训**：v6 升级时它还不存在，7 个 v5 存档当场变砖，是后来补上这套机制才救回来的 ⇒ 这次升级要**先**把它准备好）；
> ② **要加的维度得一次列全**，因为它们都动 `FEAT_S`/`FEAT_A` ⇒ 只能同一次重训；
> ③ **"打谁"（目标选择）目前完全没进网络**，那是比"加几维特征"更大的结构问题，建议单独开一版。

## 0. 现在的网络长什么样（代码事实，非推测）

- 结构：`(状态特征 ⊕ 动作特征) → 24 隐层(ReLU) → 1 个标量`，对每个**合法动作**各打一次分再 softmax
  （`policy.js` 的 `value()` / `forward()`）。
- 参数量 = `HID×FEAT_N + HID + HID + 1` = `24×137 + 49 = **3337**`（`FEAT_S=123` 状态 + `FEAT_A=14` 动作）、`HID=24`。
- **动作不是 one-hot**，而是 14 维"属性"：可负担余量 / 是否可施展 / 相对费用 / 攻击向 / 防御向 / 雷系 /
  期望伤害 / 穿透(防御·反弹·转移) / 分类 / 目标类型(enemy·self) / 连续技。
  ⇒ **两个属性完全相同的候选，在网络眼里一模一样** —— 这正是"蓄能选不了珠类型"的根因。
- **目标选择完全没有进网络**：`forward/choose` 只返回**技能 key**；t1/t2 由 `evo.js` 的启发式决定
  （"目标选择 v2"：能一击必杀先杀 → 打血量最高 → 并列随机，见 `docs/RULES-NP.md` N19）。
- **兼容机制（P0，v6 引入）**：
  - `shapeOf(params)`：从 `params.length` 反推 `featN = (len - 2×HID - 1)/HID` ⇒ 旧包自动识别为 `legacy`；
  - `features(state, pid, featS)`：先算**新**向量，再**裁掉旧版没有的那几维**
    （v5 缺的"自己跨得过环启动线"那一维用**运行时探测**定位，不硬编码下标）；
  - `value(...)` 用 `sh.featN` 当行距 ⇒ 旧权重按旧行距读，新维度根本不参与。
  ⇒ **追加维度的正确姿势**：新维度一律**追加在末尾** + 在 `features()` 里写清"旧版要裁掉哪几维"。
  ⚠️ 但**游戏侧 `unpack(o, false)` 是严格校验**（版本/长度/维度全对才收）⇒ 新版特征上线后
  **线上那一包必须重训重发**（否则页面直接拒收）。想让旧包继续在页面里跑得放宽游戏侧校验 —— 不建议：
  页面该跑的永远是"当前版本训练出来的"。

## 1. 冠军已知问题清单：哪些和参数量有关

| # | 问题 | 现状 / 证据 | 加参数能解决吗 |
|---|---|---|---|
| 1 | **蓄能选不了珠类型**（"为放电而蓄电珠"学不会） | `js/core/play.js` 的 `autoGameN` 写死 `const beadOf = p => p.elec > p.boom ? 'boom' : 'elec'`；`normPick` 也没有 `bead` 字段 | ✅ **动作特征**加"这一手要蓄哪种珠"（或把「蓄能」拆成两个候选） |
| 2 | **看不到镜面反射"复制到了什么"** | 对手槽位的 `lastSkill` 只显示 `mirror`；`policy.js` 全文没有 `guardOf` 之类的读取 | ✅ 加 1~2 维"上个动作的**有效技能**族" |
| 3 | **看不到自己身上的架势**（含复制来的 `copiedGuard`） | 特征里没有任何架势项 | ✅ 加 1~2 维（自己的 guard kind） |
| 4 | **"打谁"完全不学习** | 目标由固定启发式选（见 §0） | ⚠️ 能，但属**结构性改动**：把候选从"技能"扩成"(技能, 目标)"（候选数 × 人数）或加目标相对特征。**建议单独一版** |
| 5 | 连招 / 顺序模式识别弱 | 只有 3 步技能史 + "连续同招比例" | 🟡 可加"相邻两步转移"特征（收益不确定，不建议这轮做） |
| 6 | 长程 / 多人经济感 | 已有自己 ep + 逐对手 ep 槽位（v6） | 🟡 边际收益小（经济门槛属 **fitness** 侧，v1.5.6 已参数化） |
| 7 | 结盟 / 威胁建模 | 你已裁定"不必强求" | ❌ 不做 |
| 8 | 技能覆盖塌缩 / 摆烂（"熬"） | 靠 fitness 的熵奖励、哨声惩罚、先手激励治 | ❌ 与参数量**无关**（训练信号问题） |
| 9 | 对手池太窄 | v1.5.2 / REVIEW §10 两次实验 ⇒ 池子是**弱杠杆** | ❌ 与参数量**无关** |

**一句话**：真正卡在"表达力"上的只有 **1/2/3/4** 四项；其余都是**训练信号**问题，
加参数不会让它们变好（这一点在过去 12 个 patch 里被实验反复证实）。

## 2. 建议的"一次加全"清单（目标 `PACK_VERSION = 7`）

1. **珠类型**（动作侧）：`FEAT_A` +1~2 维 —— 「这一手蓄电珠 / 蓄爆珠」。
   ⚠️ 守门 `np-test D22` 必须继续成立：**对手**的珠类型依旧不可见，只有**自己这一手的选择**可见。
2. **镜面反射的有效技能**（状态侧）：`FEAT_S` +1 维 —— "看到的那个动作**实际会做什么**"（复制到的卡 / 是否有防御）。
3. **自身架势**（状态侧）：`FEAT_S` +1~2 维 —— 自己当前 `guardOf().kind` 的编码 + 是否持有 `copiedGuard`。
4. （可选、另开一版）**目标选择**：把候选扩成 `(技能, 目标)` + 加"目标相对特征"
   （血量差 / 是否一击必杀 / 上回合是否互为目标 / 是否打过我）—— 同时让"目标选择 v2"那套启发式退休。
   改动面最大（候选数变多 ⇒ 训练与评测口径一起变），**不建议和 1~3 挤在同一版**。

⇒ **1+2+3 = +72~120 参数（约 +2~4%）**，是"顺手一次做完"的规模；第 4 项单独排期。

## 3. 必须一起做的配套（否则会静默错位）

- `PACK_VERSION` +1、`FEAT_S`/`FEAT_A` 常量、`features()` 的**旧版裁剪规则**、`actionFeatures()` 的维度注释；
- **守门**（`tools/np-test.mjs` 加一条）：`shapeOf` 能在新旧两种形状间正确反推 **且** 旧包用新代码解码后
  逐位等于"裁剪后的新向量"（防止裁错维度导致静默错位 —— 这正是 `shapeOf` 那套机制存在的理由）；
- **换冠军五步**照旧（`tools/promote-champion.mjs` 重测重记，规则指纹与 `examScoreAtBuild` 一起更新）；
- **必须重新训练**：新维度在旧冠军里是"零权重"⇒ 行为等价于根本没有这些特征（兼容 ≠ 变强）。
