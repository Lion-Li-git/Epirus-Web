# 2026-10-19 谱系图行带灰度（§E656）—— 复算入口与读数出处

用户 10-19 晚报：**SDR 下谱系图的灰行几乎与黑行同色**（"我以前一直在 HDR 模式下看可以区分，结果这其实是 HDR 的 bug 导致的"）。
这一档把那句话量成数、改掉、再量一遍。改动只在**渲染**，不碰读法（色带 LUT / IDW 核 / 分位定标一个字没动）。

## 一、真源在哪（改代码只改这里）

| 面 | 位置 |
|---|---|
| 行带的算法与旋钮 | `champion-map/viewer.mjs` 里 `BAND_DL` ‖ `bandFillFor(bg)`（紧邻 `paintChrome` 上方） |
| 用它的地方 | 同文件 `paintChrome` 里那一格 `t.fillStyle = i % 2 ? bandFillFor(st.bg) : 'rgba(255,255,255,.0)';` |
| 换底色必须重烘纸 | 同文件 `var ck = [..., st.dim, st.bg, ...]`（§E656 之前 `st.bg` **不在键里** ⇒ 带子一旦跟底色有关，漏它就是"换底色但纸不重烘"） |
| 页面产物 | `champion-map/index.html` —— **烘出来的**，改完 `viewer.mjs` 必须跑 `node champion-map/viewer.mjs`（否则 `D234 ⑩c` 红） |

## 二、复算入口（三条命令，脚本自身不写死机器路径）

```bash
node champion-map/shot.mjs --win=2560,1600 --hash="mode=tree&bg=%2305070d" --out=/tmp/new-black.png
node docs/research/archive/2026-10-19-tree-band-grey/probe-rows.mjs /tmp/new-black.png
node docs/research/archive/2026-10-19-tree-band-grey/band-ruler.mjs /tmp/某张截图.png
```

`probe-rows.mjs` 沿一条竖扫描线把连续同色段列出来（判行带用）；`band-ruler.mjs` 出四个数（不同色数 ‖ 竖直/水平剖面的电平数与最长平台 ‖ 相邻像素跳变的中位/P99/最大）；两者共用 `png.mjs`（8bit 非隔行 PNG 的最小解码器）。
`XF` / `Y0` / `Y1` 环境变量换扫描线位置，`--x0/--x1/--y0/--y1/--col/--row` 换取样框。

## 三、读数（全部是无头 Chrome 2560×1600 截图像素量出来的，ΔL\* 按 CIE L\* 算）

| 底色档 | 黑行 | 旧灰行 | 旧 ΔL\* | 新灰行 | 新 ΔL\* |
|---|---|---|---|---|---|
| 纯黑 `#05070d` | rgb(5,7,13) | rgb(11,13,19) | **1.74** | rgb(21,23,29) | **5.83** |
| 深蓝 `#0f1522`（默认） | rgb(15,21,34) | rgb(21,27,40) | **2.87** | rgb(27,33,46) | **5.84** |
| 浅底 `#e6ebf5` | rgb(230,235,245) | **整条带子不出现**（837 行只有一种颜色） | ≈0 | rgb(213,218,228)（朝暗走） | **6.00** |

⇒ 旧的写法是一层"往透明纸上刷 2.8% 白"的洗色，抬多少**取决于纸后面是什么**：1 个 L\* 约等于刚能看见，而它给的是 1.7~2.9，浅底档干脆看不见。现在带子是**不透明色**，落点由 `BAND_DL`（默认 6）一个数说了算，与纸后面无关。

## 四、变异证明：这个旋钮**没有**自动上界

把烘出来的页面里 `var BAND_DL = 6` 改成 `60`（只改 Temp 里的副本，活跃产物一个字节没动），跑页内自检：

```
断言：93 PASS ‖ 0 FAIL        ← 灰行此时亮到 rgb(156,162,175)，比左栏统计行的字还亮
```

`inkLeft` 那条"三通道之和与底色差 > 150 才算墨"拦不住它：带子横贯整行，被当成"最左边的墨"时两帧都返回 x=0，位移差仍然是 80 px ⇒ 断言照样过。
⇒ **调 `BAND_DL` 只能靠量像素或看图**，别以为有门在管。（要不要给它配一条页内自检腿，属"加一条腿"，等用户点头。）

## 五、顺带对另一份方案的判定（另一会话写的仓外方案文件 `C:/Users/14765/Documents/Qoder/2026-10-18/6cce591b/epirus-web-banding-plan.md`，说地图底图有同心环）

那份方案的核心前提我用同一把尺量了，**不成立**：

1. **"gx/gy 被 `Math.max(40,…)` 抬到 40×40"是读错了变量**：`viewer.mjs:1283` 的 `TOT` 是**格数预算**（`clamp(dispX*dispY/225, 40000, 400000)`），不是包数 803。
2. **"一格一色"被像素否掉**：在几乎纯底图的一角（x 0.86–0.98 ‖ y 0.62–0.80，528,711 像素）实测**不同颜色 1933 种** —— 40×40 的栅格最多只有 1600 色，而这只占画布一角。
3. **"putImageData 直接当可见层、没做插值"也不对**：地板是 `viewer.mjs:2150-2151` 在**仿射变换下** `drawImage` 贴上去的，且 `imageSmoothingEnabled = true` ‖ `imageSmoothingQuality = 'high'` ⇒ 它的候选修法 1（启用插值）**本来就在生效**。
4. 但**断层是真的**：同一角实测最长平台 16 行 / 22 列、相邻跳变 P99 = 1 ‖ 最大 2 ⇒ 平滑场被量化成一条条等值带（每格颜色在 `Math.round` 处落到 8-bit）。⇒ 该做的是它的**候选修法 2（每格加有序抖动）**，不是修法 1 或 3。
5. ⚠ 它那组"689 色 / 42 电平 / 最大跳变 17"是从**用户真截图**量的，而我从页面直出的 sRGB 截图量到 32,510 色（同一尺寸的取样框）⇒ 两边不是同一个东西，差的那一段很可能就是它自己要排除的显示链路（HDR 截图被按 sRGB 解 ⇒ 低端电平被压平）。**这条我只测到"两边不一致"，没测到"是截图链路造成的"。**

⇒ 地图那半边**本轮没动**：抖动会改变画面观感，属"要不要付"的产品判断，等用户点头再做（预注册判据就用本目录这把尺：最长平台与相邻跳变 P99 必须显著下降，而不同色数与色相不许系统性偏移）。

## 七、有序抖动试做（用户 10-19 晚点名"先试一下让我看观感"）——**负结果，量在屏幕上**

试验代码不在 main 上，留在 `dither-trial.patch`（打上后 `node champion-map/viewer.mjs` 重烘；关掉对照用深链 `#dith=0`）。
做法：Bayer 4×4 阈值表按**格坐标**取模决定进位（不用随机 ⇒ 平移缩放时颗粒跟着纸走，不会逐帧闪），替掉每格那三个 `Math.round`。

同一台尺、同一视角、两张截图对比（`band-ruler.mjs` ‖ `mean-box.mjs`，纯底图一角 x 0.86–0.98 y 0.62–0.80）：

| 读数 | 关抖动 | 开抖动 | 判 |
|---|---|---|---|
| 最长平台 | 23 行 ‖ 22 列 | **24 行 ‖ 22 列** | 没降 ⇒ 等值带还在 |
| 剖面电平数 | 44 ‖ 31 | 44 ‖ 31 | 不动 |
| 相邻像素跳变 | P99 1 ‖ 最大 2 | P99 1 ‖ 最大 2 | 不动 |
| 位图不同色数 | 1933 | 1983（+2.6%） | 只在位图那一级多了一点 |
| 框内均值 | rgb(57.113, 46.904, 45.942) | rgb(57.128, 46.873, 45.960) | **读法没被带跑**（差 0.02/255） |
| 页内自检 | 93 PASS / 0 FAIL | 93 PASS / 0 FAIL（含 §E573 快路逐位等于暴力） | 没弄坏任何一条 |

**机制解释（为什么无效）**：抖动落在 259×155 的位图上，而地板是在仿射变换下 `drawImage` 放大 ~10–16 倍贴出来的，`imageSmoothingEnabled=true` ⇒ 相邻一升一降的两格被双线性**平均回原值**。所以"位图上有颗粒、屏幕上没有"。
⇒ 要真打散等值带，抖动必须落在**屏幕像素那一级**：两条路都更贵 —— ① 把地板先烘成屏幕分辨率再抖（平移/缩放时要重烘，每帧 400 万像素级的循环）；② 走 GL 片元着色器（现成的 `gl-mesh.js` 只画壳，且 `shot.mjs` 带 `--disable-gpu` ⇒ 页内自检那条路要另想）。

图：`cmp-corner.png`（左=关 ‖ 右=开，同一 128×128 角放大 3 倍）‖ `cmp-mid.png`（中段同一处理）。两张都看不出系统性差别，与上表一致。

### 七·补　用户看完之后的裁定与对本档的更正（10-19 晚，已撤）

用户的原话：**「抖动解决了 HDR 模式下的大断层，未能解决真正的小断层，而且看起来变得很奇怪。撤回去吧」** ⇒ 试验改动已从工作树撤掉（`git checkout -- champion-map/viewer.mjs champion-map/index.html`，撤后 `--part=ship-pool` 1/1 ‖ 重截同一角读数逐字回到关抖动那列：1933 色 ‖ 平台 23 行/22 列 ‖ 均值 rgb(57.113,46.904,45.942)）。

⚑ **本档上面那句"负结果"要限定范围，别读成"抖动没用"**：我量的是**无头 Chrome 直出的 sRGB 截图**，那条路上双线性会把 ±1 LSB 平均回去 ⇒ 尺上不动。而用户看的是**自己机器 HDR 那条链路**——电平本来就稀缺，±1 LSB 在那儿活了下来，**大断层确实被它消掉了**。⇒ 两件事都成立，差别在链路上不在抖动上；我这把尺对 HDR 那一段是**盲的**（"我测不到不等于没有"）。
⇒ 剩下的结论按用户的判据：真正要治的是**小断层**（用户机器低亮度那一条独立链路，见 `oled-banding-report.md`），而抖动把画面弄脏了却不治那个 ⇒ 不进 main。要再试这条路，前提是先有一条能看 HDR 那一段的尺，否则会一直得出"无效"的假读数。
